# Спецификация и дорожная карта

Статус: установщик реализован поверх YAML-схемы. Обычная Cargo
registry-сборка восстановлена. Первый настоящий Ubuntu-прогон установил Codex
и два native агента VoltAgent; расширенный прогон установил все пять CLI и
проверил локальный MCP через их конфиги. Independent Review и итоговая Validate
фиксируются в [installer reports](features/installer/run.md).

Текущие контракты клиентов и план реализации находятся в
[Research](features/installer/research-adapters.md),
[Plan](features/installer/plan.md) и
[живом Ubuntu-прогоне](features/installer/live-ubuntu.md).
Они уточняют устаревшие предположения исходной дорожной карты ниже.

## Цель и сценарий

Пользователь один раз вручную описывает личную среду в YAML и повторно запускает
`yashik init ./yashik.yaml` на Linux или macOS. Yashik устанавливает выбранные
клиенты и ресурсы в глобальное пользовательское окружение, сохраняет сведения
об управляемых компонентах и при каждом запуске приводит машину к описанному
состоянию. Первая ручная проверка реализации запланирована на Ubuntu.

Установка самого Yashik предшествует `init` и будет отдельным шагом. Способ
распространения и bootstrap ещё не выбраны; адрес скачивания и однострочник
сейчас не задаются. Целевая команда диагностики — `yashik doctor`: она читает
состояние и конфигурации, ничего не меняя.

Поддерживаемые harness IDs: `codex`, `claude`, `opencode`, `pi`, `omp`.
Yashik управляет только глобальными пользовательскими настройками и ресурсами:
CLI harnesses, MCP, skills, agents и rules. Проектная установка не входит в
объём. Авторизация в клиентах и сервисах остаётся за пользователем. Секреты
не записываются в манифест или журнал.

## Контракт YAML v1

Корневые поля: `version`, `harnesses`, `mcp`, `skills`, `agents`, `rules`.
`version: 1` выбирает версию схемы YAML. `harnesses.<id>.version` при наличии
закрепляет версию соответствующего клиентского CLI; если поле пропущено,
выбирается последняя версия по поддерживаемому рецепту и разрешается снова при
каждом `init`. Этот YAML не закрепляет версию самого Yashik. Неперечисленный
harness не устанавливается; перечисленный включён, если у него нет
`enabled: false`.

Каждый раздел ресурсов — словарь по имени. Ресурсы в корне общие и применяются
ко всем включённым harnesses. В `harnesses.<id>.<type>` можно добавить ресурс,
заменить одноимённый общий ресурс целиком или указать для него
`enabled: false`, чтобы исключить его только в этом harness. Частичного
слияния полей между общим и локальным ресурсом нет. Имена ресурсов уникальны
в пределах своего типа; одно имя в разных типах — разные ресурсы.

| Поле | Контракт |
| --- | --- |
| `source.type: git` | Требует `url`; `ref` необязателен. Доступ к приватным репозиториям идёт через уже настроенную авторизацию Git. |
| `source.type: local` | Требует `path`. Относительный путь считается от каталога YAML; он может указывать за его пределы. |
| `from` | Необязательный путь внутри корня выбранного источника. Без него используется сам выбранный объект или корень. Канонический путь, включая symlink, должен остаться внутри корня источника. |
| `install.requires` | IDs требуемых runtime/tool, например `node`; способы их установки задают проверенные platform-рецепты. |
| `install.steps` | Необязательные непустые массивы argv. Запускаются в каталоге источника без неявного shell. Это всё ещё выполнение кода из источника. |
| `transport: stdio` | Текущий контракт MCP. Другие транспорты требуют отдельного решения. |
| `run.command`, `run.args`, `run.env` | Команда и аргументы для запуска MCP. `${source}` — абсолютный корень источника; `${env:NAME}` — ссылка на переменную окружения, значение не хранится в YAML. |

Для Git полный commit SHA даёт стабильную привязку. Имя ветки или тега может
перемещаться. Если `ref` отсутствует, Yashik заново разрешает default branch
при каждом `init`; записанная точная ревизия описывает выполненный прогон и не
закрепляет `latest` навсегда. Манифест обязан явно задавать источник и шаги
установки; репозиторий сам по себе не определяет способ сборки.

Skill — каталог с `SKILL.md`. Portable agent задаёт `format: portable`,
`description` и Markdown-инструкции в `source/from`; имя берётся из ключа.
Portable rule задаёт `format: portable` и Markdown в `source/from`. Нативный
agent или rule задаётся только локально внутри соответствующего harness с
`format: native` и его исходным файлом. Адаптер сохраняет смысл и поля
portable-ресурса; если capability или формат нельзя выразить, Yashik объясняет
ограничение и спрашивает, пропустить или отменить установку этого ресурса.

Полный пример четырёх типов общих ресурсов, локального native override,
адресного отключения, Git и относительного local source приведён в
[examples/yashik.yaml](../examples/yashik.yaml). Все его адреса, версии и токены
обозначены как примеры и требуют замены.

## Поведение `init`

1. Прочитать и проверить YAML, типы, неизвестные поля, источники и допустимые
   пути. Ошибка до построения плана не должна менять машину.
2. Определить платформу, выбранные harnesses, доступные версии и фактическое
   состояние глобальных ресурсов. Для неподдерживаемого harness или resource
   спросить, пропустить его или отменить его установку.
3. Построить граф зависимостей: source → runtime/build → статическая проверка
   команды и артефакта MCP → harness binding. Проверка подтверждает наличие
   запускаемого файла и корректность локальной конфигурации, но не проверяет
   внешнюю авторизацию. Устанавливать недостающие runtime и CLI можно только по
   поддерживаемым рецептам; при необходимости запросить sudo.
4. Выполнить независимые операции. Ошибка блокирует её зависимые шаги, но не
   независимые ресурсы. Не регистрировать MCP после неудачной сборки. В конце
   показать успех, пропуски, ошибки, оставшиеся действия и точные разрешённые
   версии/ревизии.
5. Сохранить в state результат каждой операции: успех, ошибка, пропуск или
   блокировка зависимостей, с причиной и разрешённой целевой ревизией, если она
   известна. Только после успеха записывать артефакт как управляемый и обновлять
   его установленную версию, fingerprint и привязки. Секреты не логировать.

Повторный `init` сравнивает желаемое состояние из YAML, сохранённое владение и
текущее состояние машины. Он идемпотентно добавляет, обновляет или перепривязывает
ресурсы. Одинаковое имя само по себе не доказывает владение Yashik. MCP с
одинаковой эффективной спецификацией устанавливается один раз и может быть
привязан к нескольким клиентам; отличающийся локальный override получает
отдельную эффективную установку.

Перед изменением существующей настройки Yashik показывает конфликт, объясняет
разницу и спрашивает `merge` или `replace`; до записи сохраняется backup.
`merge` накладывает желаемые поля на существующую запись и сохраняет поля,
которых нет в манифесте. `replace` сбрасывает прежние настройки этого ресурса
до желаемой конфигурации. В обоих случаях адаптер сохраняет поля авторизации,
которые он распознаёт, и все соседние/неуправляемые записи общей конфигурации;
заменить весь конфиг клиента нельзя. Ручное редактирование
управляемой записи считается конфликтом и требует того же решения. Если формат
не позволяет безопасно выполнить выбранную операцию и сохранить отдельные
данные авторизации, Yashik объясняет
ограничение и предлагает пропустить или отменить установку ресурса.

Если ранее управляемый ресурс исчез из YAML, Yashik спрашивает перед удалением.
Отказ оставляет ресурс и отметку в state для последующей диагностики. Ресурс
без подтверждённого владения Yashik не удаляется.

Публичный компонент можно установить без готового токена MCP: отсутствие
авторизации не считается ошибкой всей установки. Итог указывает, когда
пользователю нужно настроить доступ. `doctor` проверяет локальные бинарные
файлы, версии, ресурсы, bindings, drift и прошлые ошибки; наличие CLI не
подтверждает вход в сервис или доступность удалённой модели.

## Архитектура и ограничения

Будущая реализация разделяет типизированный манифест и наследование, платформу
и runtime-рецепты, Git/local sources, DAG planner, argv executor,
version-aware harness adapters, state/backup/journal и интерактивный CLI.
Конфиги читаются и изменяются форматными адаптерами; обновление файла проходит
через backup и атомарную запись, где формат это позволяет. Внешние установки
не обещают общей транзакции, поэтому журнал фиксирует исход каждой операции,
включая пропуск, блокировку и сбой; владение и фактическая установленная версия
попадают в managed state только после успеха.

Поддержка клиента означает только проверенные версии и capabilities. В
исследовательской матрице есть расхождение по глобальному пути Codex skills;
его нельзя объявлять универсальным до проверки. OpenCode требует привязки
формата к версии, OMP — учёта глобального профиля. Нативный формат Pi subagents
не подтверждён: такая capability должна идти по ветке unsupported, пока не
будет выбран и проверен пакет/адаптер. Матрица первичных источников в Research
не заменяет smoke test реально установленного CLI.

Пользовательские install steps исполняют код. Массив argv устраняет неявную
интерпретацию shell, но не делает репозиторий безопасным. Автоматическая
публикация каталога, установка по handle, URL-манифест, release assets,
marketplace, удалённый MCP, экспорт текущей машины и unattended-режим не входят
в согласованный MVP. Модели, providers, permissions и hooks тоже отложены.

## Дорожная карта

| Этап | Зависит от | Результат и выходной критерий |
| --- | --- | --- |
| 0. Спецификация | Интервью и Research | README, YAML и этот план согласованы; D1–D8 проходят review/validate. |
| 1. Rust schema | 0; доступный или проверенный YAML parser | `init`/`doctor` каркас, строгая валидация и наследование реализованы; полный Linux suite прошёл на проверенных upstream source snapshots. Обычная Cargo registry resolution и macOS остаются непроверенными (M1–M2). |
| 2. Источники и планировщик | 1 | Git/local, containment, pin/latest, state и DAG; тесты источников и разрешения версий (M3–M4). |
| 3. Ubuntu vertical slice | 2; проверенные runtime/CLI-рецепты и один adapter baseline | Сквозная установка одного клиента, stdio MCP, skill и доступных agent/rule; повторный запуск и частичный сбой проверены. |
| 4. Остальные adapters | 3; подтверждённые версии и форматы | Codex, Claude Code, OpenCode, Pi и OMP; native overrides и version-specific fixtures (M9, M11). |
| 5. Reconciliation и doctor | 2–4 | Merge/replace, backups, owned-only removal, drift, journal и отчёт; проверки идемпотентности/восстановления (M5–M10). |
| 6. Bootstrap и macOS | 3–5; выбранная доставка Yashik | Рецепты runtime и sudo, чистые Ubuntu/macOS, документированная установка (M12). |
| 7. MVP release | 1–6; Review и Validate | Все обязательные M-критерии пройдены; ограничения реальных smoke tests указаны. |

До этапа 3 уточняются runtime и client CLI-рецепты. До этапа 4 — версии и
форматы adapters, portable contracts и способ Pi subagents. До этапа 6 —
доставка Yashik, источники платформенных пакетов и проверки целостности.
Реальную установку проверять в отдельном временном HOME. Linux-проверка не
подтверждает macOS, а mock не подтверждает чистую машину. Сроки реализации
оцениваются после успешной вертикали.
