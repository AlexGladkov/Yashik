# Plan: управляемая установка Herdr

## Ожидаемое поведение и границы

Манифест версии 1 принимает необязательный корневой раздел:

```yaml
version: 1
harnesses: {}
tools:
  herdr:
    enabled: true
    version: latest
```

`harnesses` остаётся обязательным; пустая карта устанавливает Herdr один раз, без CLI, MCP и привязок к harness. Отсутствующий `tools` сохраняет прежнее поведение. В записи `herdr` оба поля необязательны; значения по умолчанию — `enabled: true`, `version: latest`. `enabled: false` исключает Herdr из желаемого состояния. Разрешены только имя `herdr` и поля `enabled`, `version`; дубликаты, неизвестные поля и инструменты, `null` вместо карты, не-boolean `enabled`, неверная версия и версия схемы вне `1` отклоняются. Точная версия использует существующую строгую проверку SemVer без префикса `v`; `latest` разрешён отдельно. При `check` Yashik только проверяет манифест и показывает желаемый инструмент, не обращаясь к сети и не создавая состояние.

Yashik загружает только официальный Unix executable Herdr, сверяет SHA-256 и `herdr --version`, затем устанавливает его в пользовательский префикс. Установка не запускает интерактивный Herdr, сервер, сессии, аутентификацию, интеграции или перезапуск работающих процессов. Конфигурация, сессии и данные Herdr не принадлежат Yashik и никогда не удаляются этим рецептом. Native Windows не добавляется: Windows launcher продолжает запускать Linux Yashik внутри WSL; там действует Linux-рецепт.

## Источник, установка и владение

- Получать `https://herdr.dev/latest.json` по HTTPS с ограничением времени и размера. Основной metadata GET ограничить 20 секундами; после **ошибки сетевой/HTTP-передачи**, включая таймаут или обнаруженный неполный ответ, однократно пробовать только фиксированный официальный upstream URL `https://raw.githubusercontent.com/herdrdev/herdr/master/distribution/latest.json` с теми же HTTPS-only redirect, 20-секундным timeout и пределом размера. Разделять ошибку транспорта и локальные/защитные ошибки типом результата, а не текстом сообщения: превышение размера, ошибка запуска/capture процесса или нехватка ресурсов завершают попытку без fallback. После успешно переданного ответа первичного endpoint проверять именно его; неверный JSON, форма, версия, asset или checksum завершают установку без обращения к зеркалу. Для `latest` использовать верхний `version`, `assets` и `sha256`; для точного pin — запись `releases[version]`. Проверять структуру, точное соответствие версии и ключ платформы, 64 шестнадцатеричных символа SHA-256. Отсутствующий checksum — отказ, даже если asset существует. Зеркало не является настраиваемым endpoint; в state сохранять канонический metadata URL независимо от выбранного транспорта.
- Поддержать только Linux/macOS × x86_64/aarch64. URL бинарника должен совпадать с официальным `https://github.com/herdrdev/herdr/releases/download/v<VERSION>/herdr-<platform>`; произвольный URL из метаданных не исполнять. Скачивание через HTTPS-only redirect, bounded response и временный файл. Хэш проверять до выставления executable bit или запуска. Затем запускать только проверенный staged binary с `--version`, с таймаутом и ограниченным выводом; ожидать точно `herdr <resolved-version>`.
- Хранить проверенный executable в приватном `Paths.data/tools/herdr/versions/<version>/herdr`; активировать отдельный regular executable `Paths.bin/herdr` атомарной заменой после всех проверок. Проверять тип пути без перехода по symlink; не менять чужой файл или каталог. `Paths.bin` на Linux — `~/.local/bin`, на macOS — существующий Yashik bin path. Для версии `latest` повторный `init` разрешает актуальную версию через метаданные; для exact pin использует соответствующую запись metadata. Идентичный установленный бинарник, его mode и state дают `Unchanged` без перезаписи.
- Добавить отдельный `State.tools` с `#[serde(default)]`, не меняя `STATE_VERSION = 1`. Запись `InstalledTool` хранит id, разрешённую версию, URL/ожидаемый SHA-256, путь versioned executable, путь активного executable и fingerprint последнего. Старый `state.json` без `tools` загружается как пустая карта. Операция `tool/herdr` использует существующие intent/completed journal и `RunReport`; владение появляется только после успешной установки. Повторная установка проверяет хэши обоих записанных файлов, типы и executable mode до любых действий. Несовпадение, symlink или другой тип блокируют замену и сообщаются как drift. Неизвестный существующий `bin/herdr` блокирует установку без перезаписи; ручное освобождение пути и повторный `init` остаются понятным способом восстановления.
- При удалении `tools.herdr` или `enabled: false` спрашивать о снятии только записанной, неизменённой установки, как для CLI. Без интерактивного подтверждения сообщать `PendingRemoval` и сохранять запись. При drift сохранять файлы и `PendingRemoval`/ошибку; чужие и пользовательские данные не трогать. После подтверждения удалять только проверенные активный бинарник и принадлежащий Yashik versioned executable, когда его больше ничто не использует. Не удалять каталог настроек Herdr. Прерванный intent не создаёт презумпции владения; `doctor` показывает его как interrupted. Сбой загрузки/проверки сохраняет прежнюю рабочую версию, а следующий `init` может повторить попытку.
- `doctor` остаётся read-only: проверяет состояние, типы, mode, хэши и точную версию записанного Herdr без сетевого запроса и без запуска server/session. Изменённый или отсутствующий binary, launcher либо state даёт явный failure; отсутствие инструментов в старом состоянии не даёт ложную ошибку. Для `herdr --version` применить bounded subprocess timeout/output, не доверять PATH.

Метаданные и формат assets подтверждены [официальным `latest.json`](https://herdr.dev/latest.json); резервный источник — [файл в официальном upstream репозитории](https://github.com/herdrdev/herdr/blob/master/distribution/latest.json). [Документация Herdr](https://herdr.dev/docs/install/) описывает поддерживаемые платформы. Проверка checksum подтверждает соответствие данным издателя, а не независимую подпись.

## Реализация и зависимости

1. `src/schema.rs`, `src/validation.rs`, `src/effective.rs`: закрытый `tools.herdr`, дефолты и effective tool; сохранить обязательный `harnesses`, обновить сообщения `check` в `src/main.rs` без раннего выхода при пустом списке harness.
2. `src/install/api.rs`, `state.rs` и отдельный модуль `src/install/tools.rs`: запись установленного инструмента, официальный resolver/downloader, проверка, stage/activate, инспекция и снятие. В `tools.rs` выделить типизированный результат metadata fetch: транспортные ошибки допускают единственный переход с основного URL на фиксированное зеркало; остальные ошибки и ошибки `resolve_metadata` завершают установку. Оставить asset fetch на прежнем официальном URL и прежних ограничениях. Повторно использовать безопасные файловые и hash helpers, не вводить универсальные команды установки произвольных tools.
3. `src/install/engine.rs`, `doctor.rs` и `mod.rs`: независимая фаза инструмента под существующей блокировкой, `curl` как host dependency даже без harness, operation reports и read-only doctor. Ошибка Herdr не должна делать вид, что операция успешна; остальные желаемые ресурсы следуют существующей обработке.
4. `tests/yaml_schema.rs`, `tests/installer_state.rs`, новые или расширенные installer/CLI tests: schema, старое состояние, локальный metadata/asset fixture, success/failure/retry/retention/doctor. Добавить regression fixtures: основной metadata fetch даёт транспортную ошибку и зеркало успешно устанавливает проверенный binary; оба endpoint дают транспортную ошибку и состояние/старый executable сохраняются; успешный ответ основного endpoint с неверным JSON, версией, asset или SHA, а также превышение metadata cap, не вызывают fallback. Проверить, что asset download не переключается на зеркало. Тесты не должны зависеть от текущего live Herdr release.
5. README, действующий пример манифеста и описание схемы: короткий пример `tools.herdr`, пути, `latest`/pin и ограничения. Совместить с уже начатой фичей default manifest, не теряя её изменений.
6. Root обновляет root и Windows `Cargo.toml`/`Cargo.lock`, `scripts/install.sh` и release-facing docs до **0.3.0**, проверяет согласованность версий и publish workflow. Продуктовая фича не меняет Windows bridge, WinGet или Homebrew recipe, кроме генерируемых для нового релиза artifacts/manifests.

Execute Engineer владеет продуктовым кодом, тестами и документацией Herdr; root владеет bump/release-интеграцией и внешней приёмкой. Они работают в общей рабочей копии, сохраняют текущие правки default-manifest и не включают в релиз постороннее изменение `.agents/skills/business-feature/SKILL.md`. Отдельный Review Engineer и Tester выполняют стадии профиля после Execute; находки возвращаются исполнителю.

## Критерии приёмки и проверки

| ID | Критерий |
| --- | --- |
| H1 Schema | Старый v1 манифест работает; tool-only v1 с `harnesses: {}` проходит `check`, а отсутствие `harnesses` отклоняется; `enabled`/`version` defaults и exact pin корректны; неизвестное имя/поле, дубликат, неверная версия отклоняются с путём ошибки. `check` не пишет state и не скачивает metadata. |
| H2 Install | На Linux x86_64 и доступных native CI Linux/macOS платформах `init` выбирает правильный asset, требует checksum, проверяет hash и `--version` до активации; tool-only установка создаёт один `herdr`, не устанавливая harness. `herdr --version` совпадает с записью state. |
| H3 Safety | После транспортного сбоя основного metadata GET допускается только одна попытка фиксированного upstream metadata URL; при успехе зеркало проходит те же проверки и установка может завершиться. Если оба endpoint недоступны, неверный metadata JSON, отсутствующий release/asset/hash, checksum mismatch, wrong version, превышение metadata cap, локальный сбой, unsupported OS/arch или чужой/symlink target — прежний executable не перезаписывается и ложное владение не создаётся. На содержательных ошибках основного ответа fallback не выполняется. Сбой можно повторить. |
| H4 Reconcile | Повторный pinned `init` с тем же hash даёт `Unchanged` и не меняет inode/mtime активного бинарника. Drift файлов обнаруживается до замены. Удалённый/disabled Herdr остаётся `PendingRemoval` без подтверждения; после подтверждения удаляются лишь проверенные Yashik-owned binaries, не пользовательские данные. |
| H5 Doctor | Старый state загружается; doctor без tools работает. Для Herdr он read-only, проверяет оба файла и version; tampering, missing binary и interrupted intent отображаются как failure/interrupted. |
| H6 Release | Версии root/Windows/script = 0.3.0. `cargo fmt --check`, `cargo test --locked`, `cargo clippy --locked --all-targets -- -D warnings`, Windows crate tests и release workflow проходят. Draft содержит все восемь ожидаемых assets и SHA256SUMS; после H7 draft опубликован как v0.3.0, публичные ссылки, installer и checksums подтверждены. |
| H7 Server | До публикации на `test-server-root` в `/root/opt/yashik-setup` запустить Yashik из упакованного CI artifact с `yashik-compose.yaml`, включающим Herdr; проверить `check`, первый/повторный `init`, `doctor`, `herdr --version`, state и отсутствие неожиданных изменений пользовательских данных. Зафиксировать успешную установку при недоступном основном metadata GET и работоспособном фиксированном зеркале либо фактическую причину нового отказа; прежний неуспешный `init` успехом не считать. После публикации отдельно проверить публичный installer и версию Yashik. Зафиксировать фактические версии, команды и результат в `validation.md`. Linux x86_64 проверка не заменяет macOS или native Windows runtime. |

`review.md` фиксирует независимые находки с severity и местом; `validation.md` — команды, результаты, ссылки CI/release и непроверенные платформы. При блокирующем замечании исправить код и повторить Review/Validate затронутого поведения. Тег — после локальных тестов и независимой проверки; публикация — после серверной приёмки CI artifact. Опубликованный релиз не перезаписывать.
